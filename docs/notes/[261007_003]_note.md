### 논의: TSX의 동적 수정
- 질문: TSX로 작성하면 동적으로 수정할 수는 없는지.
- 정리:
  - 실행 중인 브라우저에서 TSX 파일을 직접 고치는 것은 **불가**(TSX는 빌드 때 컴파일되는 소스이고, 단일 HTML export 결과물은 더 그러함).
  - **파일 수정 → 즉시 반영**은 가능하고 지금 이미 동작함(Claude Code나 에디터가 파일을 고치면 Vite HMR이 미리보기를 갱신).
  - 화면에서 고친 내용을 TSX에 저장하는 방식은 가능하지만 공이 큼: 개발 서버에 저장 API를 두고 `ts-morph` 같은 도구로 TSX를 코드로 분석해 해당 부분만 다시 씀. 슬라이드 맨 위 `text` 객체처럼 **단순한 값**만 안전하게 바꿀 수 있음.
  - TSX 문자열을 브라우저에서 즉석 컴파일하는 방식은 무겁고, AI가 만든 코드를 실행하는 보안 문제가 있어 비추천.
  - 문구를 데이터(JSON)로 분리하면 UI가 JSON만 바꾸면 되어 쉬움(노트 001의 "구성까지 데이터" 확장 후보와 같은 방향).
- **결정: "동적 수정"은 파일 수정을 뜻한다.** 파일을 고치면 미리보기에 바로 반영되는 방식(Vite HMR)으로 충분하며, 화면에서 직접 고쳐 TSX에 저장하는 기능은 만들지 않는다.
- 유지할 규칙: `text` 객체는 **단순한 값(문자열, 배열, `badge()` 같은 헬퍼 호출)으로만** 두고 로직을 섞지 않는다(나중에 필요해지면 자동 수정이 쉽도록).

### 결정: 배포 방식
- **서비스로 배포하지 않는다.** 사용자는 **레포지토리를 내려받아 로컬에서** 사용한다.
- 영향:
  - AI(Claude Code 등)가 로컬 저장소의 TSX를 직접 고치는 방식이 기본 사용 방식이 된다.
  - AI가 만든 TSX를 서버에서 실행하는 보안 문제(노트 001, ADR [261007_001] ADR-2, ADR [261007_002] ADR-5)는 해당하지 않는다. 사용자가 자기 컴퓨터에서 자기 코드를 실행하는 구조이다.
  - 웹 서버, 인증, 호스팅, 다중 사용자는 고려하지 않는다.
  - "서비스" 및 "나중에 agent 연동"이라고 적은 기존 표현(CLAUDE.md의 개요 문장, ADR [261007_002] ADR-5)은 이 결정과 맞지 않아 **수정이 필요**하다(미반영).

### 결정: 강의는 강의별 별도 저장소로 관리
- 도구 저장소(이 저장소)는 `courses/` 아래를 추적하지 않고, `courses/{강의}` 폴더마다 자기 `.git`을 가진 **별도 저장소**로 관리한다. `course` = 하나의 전체 강의 = 하나의 저장소.
- `.gitignore`: `courses/*`, `!courses/sample/`. 샘플(`courses/sample`)은 도구와 함께 배포되는 예제로 계속 추적한다. (무시 규칙 동작 확인함)
- 도구 저장소를 `git pull`로 업데이트해도 강의 파일과 섞이지 않는다. 강의 저장소는 비공개로 둘 수 있다.
- 대안으로 검토했으나 채택하지 않음: git submodule(조작이 번거로움), 저장소 밖 폴더 지정(`COURSES_DIR`; 밖에 있는 파일은 `react` 등을 찾지 못해 `resolve.dedupe`, `fs.allow` 설정이 필요하고 프로토타입 확인이 필요함. 나중에 확장 가능).
- 주의: 강의 저장소의 슬라이드가 도구의 API(`@/elements` 등)에 의존하므로, 도구가 바뀌면 강의가 깨질 수 있다. API 변경에 대한 버전 관리 방법은 미정.

### 논의: 슬라이드 마스터 구현 (제안, 미확정)
- 전제: `slide-master`는 PPT 슬라이드 마스터와 같은 개념이며 안에 `background`와 `layout[]`을 가진다. layout마다 background를 가지고, 기본은 master background를 상속한다(ADR [261007_002] ADR-1). 강의가 별도 저장소가 되었으므로 도구 공통 마스터와 강의별 마스터를 나눠야 한다.
- 제안: **두 단계**.
  1. 도구가 제공하는 **기본 마스터**: `src/masters/default/` (모든 강의 공통).
  2. **강의 마스터**: `courses/{강의}/master.tsx`. 기본 마스터를 확장(`extendMaster(defaultMaster, {...})`)해서 로고, 색 등 강의별 차이만 덮어쓴다. 강의 마스터가 없으면 기본 마스터를 쓴다.
- 마스터 정의 예(개념): `defineMaster({ background, common: [로고, 페이지 번호 등 공통 요소], layouts: { title, content, ... } })`. layout의 종류는 나중에 정한다(결정 유지).
- 슬라이드가 layout을 고르는 방식(예: `<Slide layout="two-column">`)과 슬롯 구조는 layout을 정할 때 같이 정한다.
- 렌더링: 미리보기와 export가 슬라이드를 해당 강의 마스터로 감싸서 그린다(마스터 → layout → 슬라이드 element 순).
- PPTX export 대비: 마스터에서 온 요소에 표시(예: `data-origin="master"`)를 달아 두면 PPTX 변환 때 진짜 PPT 슬라이드 마스터로 올릴지, 슬라이드마다 복제할지 선택할 수 있다(프로토타입에서 결정).
- 테마 토큰(색, 크기, 여백)은 CSS 변수이며 강의 마스터가 값을 덮어쓸 수 있다. 폰트는 R/B 두 가지로 제한한다(ADR [261007_002] ADR-4).
- 미확인: 도구 공통 마스터가 필요한지 vs 강의가 각자 완결된 마스터를 가지는지, 슬라이드마다 layout/background를 덮어쓸 수 있게 할지, chapter/section 단계의 마스터 덮어쓰기가 필요한지.

### 논의: 여러 개의 슬라이드 마스터 (제안, 미확정)
- 요구: 강의 특성상 다른 마스터를 써야 하는 경우가 있으므로 `src/` 아래에 마스터를 여러 개 둘 수 있어야 한다.
- 구조: `src/masters/{id}/index.tsx`. `import.meta.glob("./*/index.tsx")`로 폴더를 자동 등록하고 **폴더 이름이 마스터 id**. `_`로 시작하는 폴더(`_shared`: 로고, 페이지 번호, 공통 layout 등 공용 부품)는 등록 제외. `src/masters/index.ts`에 `defineMaster`, `extendMaster`, 조회 함수. 마스터 간 재사용은 `extendMaster(masters.default, {...})`.
- **결정: 마스터는 course 단위로 고른다.** `courses/{강의}/meta.ts`의 `master` 필드(선택 사항)로 마스터 id를 지정하고, 없으면 `default`를 쓴다. chapter, section, slide 단위로 마스터를 바꾸는 방식은 두지 않는다. (앞서 제안한 slide > section > chapter > course > default 우선순위는 폐기)
- 영향: 강의 하나는 마스터 하나만 쓰므로 chapter 하나가 되는 단일 HTML, PPTX, PDF에도 마스터가 하나만 들어간다(PPTX의 슬라이드 마스터 여러 개 기능은 쓰지 않아도 됨). 마스터를 고르는 로직이 단순해진다.
- PPTX 대응: PPT는 한 파일에 슬라이드 마스터를 여러 개 둘 수 있어 이 구조와 자연스럽게 대응한다.
- 강의 전용 마스터(선택): `courses/{강의}/masters/{id}/index.tsx`. 조회 순서는 강의 폴더의 `masters/` → 도구의 `src/masters/`. 도구 저장소를 건드리지 않고 강의별로 마스터를 추가할 수 있다. 앞서 제안한 `courses/{강의}/master.tsx` 단일 파일 방식은 이 구조에 흡수된다.
- 안전장치: 존재하지 않는 id는 사용 가능한 마스터 목록과 함께 오류로 알린다. 미리보기 상단 바 `children`에 마스터 선택 드롭다운을 넣어 비교할 수 있다(개발용).
- **결정: 강의 전용 마스터를 구조에 포함한다.** 강의 저장소 안에서 자기 마스터를 가질 수 있도록 `courses/{강의}/masters/{id}/index.tsx`를 지원한다.
  - 마스터 id 조회 순서: **① `courses/{강의}/masters/{id}` → ② `src/masters/{id}`** → 둘 다 없으면 사용 가능한 마스터 목록과 함께 오류. 같은 id가 양쪽에 있으면 강의 전용이 우선한다.
  - 강의 전용 마스터도 `extendMaster(...)`로 도구 마스터를 확장할 수 있다.
  - 강의 폴더가 `courses/` 아래(프로젝트 루트 안)에 있으므로 `import.meta.glob("/courses/*/masters/*/index.tsx")`로 읽을 수 있고 `react` 해석 문제도 없다(저장소 밖 폴더 지정 방식과 다름).
  - 주의: 강의 전용 마스터가 도구 API(`defineMaster`, `extendMaster` 등)에 의존하므로 도구 변경 시 강의가 깨질 수 있다(API 버전 관리는 미정).
- 미구현: 마스터와 layout은 아직 코드로 만들지 않았다(layout 종류는 나중에 정함).

### 미결 사항 (노트 002에서 이어짐)
- slide 폴더 이름 규칙 확정(현재 샘플은 `sl.N_이름`, 에이전트의 가정).
- 단일 HTML export에 뷰어(스테이지 축소 표시, 이전/다음, 방향키)를 포함할지.
- PPTX/PDF의 출력 단위(chapter별 파일 등).
- PDF 생성 방식: HTML을 실제로 인쇄해 보고 결정.
- `layout`의 종류와 PPT 슬라이드 레이아웃과의 관계, PPTX를 만들 때 진짜 슬라이드 마스터를 쓸지(나중에 정함).
- 배포 방식 결정에 맞춰 기존 문서의 "서비스", "agent 연동" 표현을 고칠지(CLAUDE.md 개요, ADR [261007_002] ADR-5).
- 줄바꿈 정리: 저장소에 LF/CRLF가 섞이지 않도록 `.gitattributes`(예: `* text=auto eol=lf`)를 둘지.
- 미리보기 화면 확인 실패의 원인(위 참조). 시도 방법: 개발 서버를 `--host 127.0.0.1`로 다시 띄워 IPv4로도 응답하게 한 뒤 재시도, 안 되면 다른 브라우저(Browser 1)로 시도하거나 직접 확인.
