### 설계 논의: 중간표현(IR)
- 요구사항: AI와 대화하며 강의자료를 만들고, 같은 자료를 HTML / PPT / PDF로 변환할 수 있어야 한다. 편집이 쉬운 중간표현 단계가 필요하다.
- 권고안: 슬라이드 단위의 **JSON 기반 구조화 문서(블록 트리)** 를 단일 원본(source of truth)으로 두고, 출력 포맷별 렌더러를 둔다.
  - 구조: `Deck → Slide → Block[]` (title, text, bullets, image, code, table, quote, notes 등), 블록마다 안정적인 `id`.
  - AI는 전체 재생성 대신 `id` 기준 부분 수정(JSON patch)을 하도록 한다.
  - 스키마(JSON Schema/Zod)로 검증하고, 렌더러는 IR을 읽기만 한다.
  - 출력: HTML(템플릿/React), PPTX(`python-pptx` 또는 `pptxgenjs`), PDF(HTML을 Playwright 등으로 인쇄하여 생성).
- 대안: Markdown 확장(Marp/Slidev 계열)은 사람이 읽고 쓰기 쉽지만, 구조적 편집과 PPT 변환의 정밀도가 낮다.
- 수정(사람이 직접 편집해야 한다는 요구 추가): JSON은 사람 편집에 불리하므로 **Markdown 기반 텍스트를 원본**으로 두고, 파싱한 AST(Deck → Slide → Block)를 검증/변환에 사용하는 방식으로 변경 권고.
  - 슬라이드는 `---`로 구분, 레이아웃과 `id`는 주석 또는 `{#id}`로 표기. AI는 블록이 아니라 슬라이드 단위로 수정.
  - 확장 문법은 최소화(레이아웃, notes, 이미지 속성 정도). 파싱 오류는 줄 번호와 함께 보고.
  - 웹 에디터 UI로 블록 단위 편집을 할 계획이면 JSON 원본이 다시 유리함 → **편집 방식(파일 직접 편집 vs 웹 UI)이 미정.**

### 설계 논의: Markdown의 표현력 한계 극복
- 문제: 인라인 뱃지, 이미지/표 배치가 순수 Markdown으로는 어렵다.
- 해결 방향: **Markdown + directive 확장(`remark-directive` 등) + 레이아웃 슬롯**.
  - 인라인 뱃지: `:badge[추천]{color=green}`
  - 이미지: `![설명](a.png){width=50% align=right caption="..."}` (좌표가 아니라 의미로 지정)
  - 복잡한 표(셀 병합): 별도 `::: table` 블록 또는 CSV 블록
  - 다단 배치: `{layout=two-column}` + `::: left` / `::: right` 슬롯. HTML은 CSS Grid, PPTX는 레이아웃 placeholder로 매핑.
- 대안 평가: Pandoc(프로토타입용, PPTX 레이아웃 제어 제한), MDX(표현력 높지만 작성/PPTX 변환 어려움), Typst/AsciiDoc(PPTX 출력 없음), Tiptap/ProseMirror + JSON(WYSIWYG).
- 한계: Markdown 계열은 "내용 + 레이아웃 선택"까지만 가능. 자유 배치(드래그, 좌표, 도형 위 주석)가 필요하면 JSON 원본 + WYSIWYG 에디터로 가야 한다.
- 미결 판단 기준: 자유 배치 필요 → JSON + WYSIWYG / 정해진 레이아웃 채우기로 충분 → Markdown + directive (파일 직접 편집).

### 요구사항 확정: 산출물과 기준 포맷
- 최종 강의자료: HTML / 납품자료: PPT / 수강생 배포용: PDF.
- **PPT를 기준으로 레이아웃을 설계**한다. 비율은 16:9 (13.333 × 7.5 in, 1920×1080 비율).
- 결론: 자유 배치가 아니라 "정해진 레이아웃 채우기" 방식 → Markdown + directive 원본이 유력. (편집 방식이 파일 직접 편집인지 웹 UI인지는 여전히 미확인)
- 구조: 레이아웃 스펙(영역 이름 + 캔버스 비율 좌표)을 단일 정의로 두고 PPTX 렌더러(기준)와 HTML 렌더러가 공유. PDF는 HTML을 `@page { size: 13.333in 7.5in }`로 인쇄.
- PPT 제약과 대응:
  - 인라인 뱃지: PPT는 문장 중간에 pill 도형 불가 → PPTX는 색상/하이라이트 run, HTML은 pill. 또는 독립 영역에만 허용.
  - 텍스트 넘침: 영역별 최대 줄 수/글자 수 규칙과 초과 경고.
  - 표: 네이티브 표 사용, 행 수 제한. 코드: 고정폭 텍스트박스 + 토큰별 색상 run.
  - 이미지: `contain`/`cover` 맞춤 모드만. 폰트: 배포 가능한 폰트(맑은 고딕, Noto Sans KR 등)로 제한.
  - 애니메이션/호버: PPT 비호환이므로 HTML 전용 또는 미사용.
- 리스크: PPTX와 HTML→PDF 결과가 완전히 같지 않을 수 있음. PPT를 LibreOffice로 PDF 변환하는 방법은 PPT와 더 비슷하지만 품질이 낮음. 프로토타입으로 비교 후 PDF 경로 확정.
- 도구 후보: PPTX는 `python-pptx`(템플릿 placeholder 채우기) 또는 `pptxgenjs`, PDF는 Playwright `page.pdf()`.

### 논의: HTML 기준으로 만들고 PPT/PDF로 포팅하는 방식
- 가능하지만 HTML→PPT가 가장 어려운 방향. 납품 PPT가 편집 가능해야 하므로 스크린샷 삽입 방식은 제외하고 **DOM 추출 방식**(렌더링된 DOM의 위치/스타일을 읽어 네이티브 텍스트박스/표/이미지로 변환)이 전제.
- 구조: Markdown → AST → HTML(1920×1080 고정 스테이지) → PDF(인쇄) / DOM 추출 → PPTX. 레이아웃 계산을 브라우저가 맡으므로 좌표 스펙 공유가 불필요하고 PDF는 HTML과 동일.
- 조건/위험:
  - 슬라이드에서 쓸 CSS를 PPT 호환 부분집합으로 제한 (그라데이션, 복잡한 그림자, 복잡한 Grid/Flex, 가상요소 장식, 애니메이션 제외).
  - 폰트 메트릭 차이로 PowerPoint에서 줄바꿈이 달라질 수 있음 → 같은 폰트, 텍스트박스 여유 폭, 넘침 검사.
  - 인라인 뱃지는 텍스트 run으로 변환되어 pill 모양이 사라짐.
  - 변환은 단방향: PPT에서 수정한 내용은 HTML/원본에 반영되지 않음.
- 비교: HTML 기준은 개발이 빠르고 미리보기가 정확하나 PPT 품질이 변환기에 좌우됨. PPT 기준(레이아웃 스펙 공유)은 PPT 품질이 안정적이나 렌더러 두 개와 좌표 맞춤 필요.
- 판단 방법: 슬라이드 3~4종(제목+본문, 2단, 표, 이미지)을 HTML로 만들고 `dom-to-pptx` 계열 도구로 변환해 PowerPoint에서 열어 품질 확인. 괜찮으면 HTML 기준, 어긋남이 심하면 PPT 기준으로 전환.

### 논의: IR에서 같은 스타일로 PPT/HTML 각각 렌더링
- 방향: Markdown → AST(내용) + 테마(스타일 토큰) + 레이아웃 스펙(영역 좌표)을 단일 입력으로 두고, HTML 렌더러와 PPTX 렌더러가 각자 출력. PDF는 HTML 인쇄. (앞서 논의한 "PPT 기준 + 레이아웃 스펙 공유"에 스타일 공유를 더한 형태)
- 스타일은 CSS가 아니라 양쪽이 표현 가능한 **토큰**으로 정의 (폰트, 색상, 글자 크기, 여백). HTML은 토큰으로 CSS 생성, PPTX는 슬라이드 마스터/run 속성에 매핑. 토큰에 없는 스타일은 사용 불가.
- 남는 위험: 브라우저와 PowerPoint의 줄바꿈 차이 → 영역별 최대 글자/줄 수 규칙, 넘침 경고, 렌더러 간 스크린샷 비교 테스트.
- 비교: HTML 기준 후 변환은 초기 비용이 작지만 변환기 한계에 계속 부딪힘. IR + 공유 스타일은 초기 비용이 크지만 PPT 품질이 안정적이고 유지보수가 쉬움. 부담되면 레이아웃 2~3종, 블록 3~4종으로 줄여 시작.

### 논의: PPT 형식에 맞춰 HTML 폭 등을 재계산
- 방식: AST + 테마 + 레이아웃 스펙 사이에 **레이아웃 엔진** 단계를 추가. 폰트 파일로 글자 폭을 측정(`fontkit`, `opentype.js`; 브라우저 `measureText`는 구현 의존적이라 기준으로 부적합)해 줄바꿈, 줄 수, 블록 높이를 계산하고, 확정된 지오메트리를 HTML과 PPTX가 공유. 넘침 검사도 이 단계에서 처리.
- 한계: PowerPoint의 실제 줄바꿈(한글 어절/글자 단위, 자간, 커닝)을 완벽히 재현하기 어려움. PPTX에 줄바꿈을 강제로 박으면 납품 후 편집이 불편해짐 → PPTX는 박스 폭에 3~5% 여유를 두고 자동 줄바꿈에 맡김.
- 가벼운 대안: HTML 측정값에 보정 계수(예: ×1.03) 적용. 구현은 쉽지만 폰트/크기마다 달라 정확도 낮음.
- 결정(잠정): 측정 계산은 넘침 검사와 크기 결정에만 사용하고 줄바꿈은 각 렌더러에 맡김. 부족하면 HTML 쪽만 줄바꿈을 고정하는 단계로 확장.

### 결정(잠정): HTML 기준으로 만들고 비율 환산으로 PPT 포팅
- 이유: HTML이 디자인 표현력이 높아 결과물이 더 예쁨. 시작 비용이 가장 낮음.
- 환산: 스테이지 1920×1080px 고정 → 13.333×7.5in. 1px = 1/144in = 0.5pt (폰트 48px = 24pt), 좌표는 px × 6350 EMU. `getBoundingClientRect()` 값에 곱해서 사용.
- 비율만으로 안 맞는 부분:
  - 텍스트박스 내부 여백: PowerPoint 기본값이 있으므로 모두 0으로 지정.
  - 줄 간격: CSS `line-height`와 PowerPoint 줄 간격(폰트 높이 대비 %)은 의미가 달라 환산 식 필요.
  - 줄바꿈: 박스 폭에 3~5% 여유, HTML의 줄 수를 읽어 PPTX 넘침 검사.
  - 첫 줄 세로 위치가 몇 px 다를 수 있음.
  - PPT로 못 옮기는 CSS(그라데이션, 복잡한 그림자, 가상요소)는 사용 금지 규칙 필요. HTML 기준의 가장 큰 함정.
- 목표 수준: PPT에서 편집 가능하고 대체로 비슷하게 보이는 수준 (픽셀 단위 일치는 목표 아님).
- 확정 조건: 프로토타입(제목+본문, 2단, 표, 이미지)으로 어긋남 정도 확인.
- 참고: HTML과 PPTX가 둘 다 XML 계열이라고 직접 변환이 쉬운 것은 아님. HTML은 흐름 레이아웃(최종 좌표가 마크업에 없음), PPTX(DrawingML)는 모든 도형에 좌표(`a:off`, `a:ext`)와 run별 스타일이 명시됨. 그래서 XSLT식 변환이 아니라 브라우저가 계산한 결과(`getBoundingClientRect`, `getComputedStyle`)를 읽어서 만들어야 함. 표(`table`↔`a:tbl`, `colspan`/`rowspan`↔`gridSpan`/`rowSpan`)와 문단/run은 구조가 비교적 직접 대응됨. PPTX는 zip 패키지(여러 XML 파트, `.rels`, 마스터, 레이아웃, 미디어)라 XML을 직접 쓰지 않고 `pptxgenjs`/`python-pptx`로 패키징.

### 논의: 1차 HTML 작성 → 위치 추출 → 2차 PPTX 포팅 (파이프라인 확정안)
- 단계: (1) Markdown/템플릿 → HTML(1920×1080) → (2) Playwright로 열어 `page.evaluate()`에서 DOM 순회, 위치/계산된 스타일 수집 → 장면 JSON → (3) 장면 JSON → PPTX(`pptxgenjs`/`python-pptx`), HTML → PDF(인쇄).
- 장면 JSON = 레이아웃이 확정된 파생 중간표현 (요소 종류, x/y/w/h, runs[text, font, size, bold, color], image src, table rows). 사람이 편집하는 원본은 Markdown/HTML이고 장면 JSON은 변환 때마다 자동 생성하므로 편집 편의성을 고려할 필요 없음.
- 추출 규칙은 명시적으로: HTML에 `data-pptx="text|shape|image|table"` 표시. 표시 없는 요소는 무시/경고하여 PPT로 못 가는 HTML이 조용히 깨지지 않게 함.
- 만들 것: 슬라이드 템플릿/컴포넌트(PPT로 옮길 수 있는 것만), DOM 추출기, 장면 JSON→PPTX 변환기(좌표 환산, 여백 0, 줄 간격 환산), 검증기(넘침, 미지원 CSS 감지).
- 시작 순서: 슬라이드 1~2장 직접 HTML 작성 → 추출기로 장면 JSON 확인 → PPTX 변환 후 PowerPoint에서 HTML과 겹쳐 비교.
- 기술 스택 후보: Playwright 중심이므로 Node/TypeScript가 자연스러움 (미확정).

### 논의: SSOT를 Markdown 대신 TypeScript(TSX)로
- 문제 제기: Markdown이 SSOT이면 표/그림/텍스트 배치가 부자연스러울 것.
- 제안: **TSX 컴포넌트를 원본(SSOT)** 으로 하고 파이프라인은 유지: TSX → HTML(React SSR) → Playwright 위치 추출 → PPTX / PDF.
  - 예: `<Slide layout="two-column"><Left>...</Left><Right><Figure src fit="contain"/></Right></Slide>`, 뱃지는 `<Badge color="green">` 컴포넌트.
- 장점: 배치가 props로 명시됨, 컴포넌트 재사용, 컴파일러/타입 검증, AI 출력 오류를 바로 걸러냄, 개발 스택이 Node/TypeScript로 통일.
- 주의:
  - 비개발자(강사)가 직접 편집해야 하면 진입장벽 → 에디터 UI 또는 Markdown 병행 필요.
  - AI가 만든 TSX를 서버에서 그대로 실행하면 보안 위험 → 선언형으로 제한(허용 컴포넌트/props만, `import`/함수 호출 차단). 로컬 도구로만 쓰면 위험 작음.
  - 슬라이드에 반복문/조건문 등 로직을 넣지 않는 규칙 필요.
- 절충안: 구조/배치는 TSX, 글이 많은 부분은 `<Md>` 안에 Markdown 문자열 허용.
- 결정(잠정): TSX(선언형으로 제한)를 원본으로 채택. 편집 주체가 비개발자인지 확인 필요.

### 결정: TSX 채택 + 문구(text)를 별도 변수로 분리
- 구조(`deck.tsx`)와 문구(`content.ts`)를 분리. 문구만 고치면 코드를 건드리지 않아도 되고, AI 수정 대상이 데이터로 한정되어 코드 실행 보안 부담이 줄며, diff 검토가 쉽고, 다국어 확장이 쉬움.
- 파일 구성: `decks/<이름>/deck.tsx`(슬라이드 순서/레이아웃), `content.ts`(문구, `as const`), `assets/`; 공용 컴포넌트는 `src/components/`(Slide, TwoColumn, Badge, Figure 등).
- 슬라이드 id(`s1`, `s2`)를 문구 키로 사용 → AI에게 "s2.left만 수정" 식으로 지시 가능.
- 고려할 점:
  - 문장 중간 뱃지/굵게 같은 인라인 서식은 순수 문자열로 표현 불가 → 문자열 안에 최소한의 인라인 문법(예: `[[badge:green|동적]]`) 허용, 렌더러가 파싱.
  - 두 파일을 오가야 하므로 슬라이드가 많아지면 `content`를 슬라이드별 파일로 분리.
  - 슬라이드 삭제/이동 시 고아 키 발생 가능 → 타입으로 잡고 미사용 키 검사 추가.
  - 레이아웃 변경은 여전히 `deck.tsx` 수정(개발자/AI 몫).
- **규칙: 하나의 슬라이드는 1개의 tsx 파일로 만든다.** AI 수정 범위가 한 파일로 한정되고, diff/검토 단위가 슬라이드와 일치하며, 슬라이드 한 장만 렌더링/추출해 빠르게 미리볼 수 있음. 위의 "두 파일을 오가는 불편"과 "고아 키" 문제도 줄어듦.
  - 구조 제안: `decks/<이름>/deck.ts`(순서와 메타를 담은 매니페스트), `slides/s01-title.tsx` 형태의 슬라이드 파일, `assets/`.
  - 문구는 해당 슬라이드 파일 맨 위의 `text` 객체로 둠(잠정). 다국어가 필요해지면 그때 분리.
  - 순서의 기준은 `deck.ts`의 배열. 파일명 번호는 읽기 편의용으로만 사용(중간 삽입 때 이름을 모두 바꾸지 않기 위함).
- 확정: 문구는 슬라이드 파일 맨 위 `text` 객체로 두고, 순서는 `deck.ts` 배열로 정한다.
- **인라인 서식(문장 안에 텍스트와 뱃지가 섞인 경우)은 세그먼트 배열로 표현**. 문자열 안 문법(`[[badge:...]]`)은 쓰지 않음(파서와 이스케이프 부담).
  ```ts
  left: ["값을 담는 이름표", ["타입은 ", badge("동적", "green"), "으로 결정"]]
  ```
  - 타입: `type Inline = string | Badge | Bold | Code | Link`, `type Sentence = string | Inline[]`. 헬퍼 `badge(text, color)`, `bold(text)` 등.
  - 장점: 파서 불필요, 색 이름 등 타입 검사, 배열 항목이 PPTX run에 1:1 대응(문장=`a:p`, 항목=`a:r`), AI 출력이 안정적.
  - 주의: 공백은 문자열에 직접 포함해야 함(빠지면 `타입은동적으로`) → 검사 규칙 고려. 뱃지가 많으면 장황해지므로 헬퍼 이름을 짧게. 다국어 시 문장이 조각나 번역에 불리(한국어만인 지금은 보류). PPTX에서는 pill 모양이 사라지고 색/굵기/하이라이트 run으로 표현.
  - 뱃지 pill을 PPT 도형으로 만들어 재활용하는 방안 검토: 도형 생성(`addPill(slide, x, y, text, color)`)은 쉬우나 도형은 텍스트 흐름에 끼지 못하고 좌표에 고정되므로, 문장 중간에서는 PowerPoint 줄바꿈이 달라지면 어긋남.
    - 방법 1(도형 겹치기): HTML 뱃지 위치를 `getClientRects()`로 읽어 도형 배치. 어긋남 방지를 위해 뱃지 있는 문장을 앞 텍스트/pill/뒤 텍스트의 세 텍스트박스로 분리하면 안정적이나 PPT 편집 시 흐름이 깨지고 한 줄 문장에만 적용 가능.
    - 방법 2(텍스트 하이라이트 `<a:highlight>`, `pptxgenjs`의 `highlight` 옵션): 흐름 유지. 둥근 모서리/안쪽 여백 없음, 구버전 PowerPoint에서 무시될 수 있음 → 프로토타입에서 확인 필요.
    - 방법 3(배치 규칙): 줄 맨 앞/독립 라벨 위치는 pill 도형 허용, 문장 중간은 하이라이트 run.
    - 결정(잠정): 하이라이트를 기본으로 하고, 줄 맨 앞과 독립 라벨 위치만 pill 도형 허용. HTML 뱃지 디자인도 하이라이트에 가깝게(작은 모서리, 작은 여백) 잡아 두 포맷의 차이를 줄임.
  - 인라인 요소는 `badge`, `bold`, `code` 세 가지로 시작하고 필요할 때 하나씩 추가(요소마다 PPTX 매핑도 추가되므로).
- 확장 후보: 구성까지 데이터(`{ id, layout, title, left, right }`)로 두고 TSX는 컴포넌트 라이브러리로만 사용. 구조 변경이 거의 없다고 확인되면 전환.

### 결정: PPTX는 출력 전용 (수정은 원본 TSX에서만)
- PPTX는 항상 원본(TSX)에서 포팅해 생성하고 직접 편집하지 않는다. 수정은 원본에서만 하고 다시 생성.
- 이 결정으로 **아래 앞선 잠정 결정들이 대체됨**: 박스 폭 3~5% 여유, 줄바꿈을 PowerPoint에 맡김, 줄 간격 환산 중심 접근, 뱃지의 하이라이트 기본안, "PPT로 못 가는 CSS 금지" 규칙(완화).
- 새 방식:
  - 텍스트: `Range.getClientRects()`로 브라우저가 실제로 나눈 **줄 단위 텍스트와 좌표**를 읽어 **줄마다 텍스트박스 하나**, 자동 줄바꿈 끔, 내부 여백 0. PowerPoint가 줄바꿈을 다시 할 수 없어 줄 수 차이 위험이 사라짐. 넘침 검사 불필요.
  - 뱃지: HTML 뱃지 좌표에 pill 도형(둥근 사각형 + 글자)을 그대로 배치하고 앞뒤 텍스트도 같은 줄의 별도 텍스트박스로 고정. 하이라이트 대신 HTML과 같은 모양 사용. `addPill(slide, x, y, text, color)`로 재활용.
  - 복잡한 CSS(그라데이션, 복잡한 그림자, 장식): 해당 영역만 PNG로 렌더링해 그림으로 삽입(이스케이프 해치). 텍스트/표/단순 도형은 네이티브 유지.
- 확정 사항:
  - 글자 세로 위치 차이는 폰트별 **보정값**으로 맞춘다(프로토타입에서 측정).
  - 폰트는 **정해 둔 폰트만** 사용한다. 폰트: **NanumSquare** (L/R/B/EB 4종, 아래 항목 참조).
  - **굵기는 역할(테마 토큰)이 정하고, 텍스트 변수에는 문장 중간 강조만 표시**한다. 제목/본문/캡션처럼 역할로 정해지는 굵기는 컴포넌트와 테마가 적용하므로 텍스트에 표시하지 않고, 문장 안에서 굵기가 바뀌는 경우만 `bold("...")`로 표시. 텍스트 변수에 폰트 이름(`NanumSquareB` 등)을 직접 쓰지 않음(폰트 변경 시 모든 슬라이드를 고쳐야 하므로).
    ```ts
    fonts: { heading: "NanumSquareEB", body: "NanumSquareR", emphasis: "NanumSquareB", caption: "NanumSquareL" }
    ```
  - 확인 필요: Windows에 설치했을 때 PPTX가 인식하는 폰트 패밀리 이름(굵기별 별도 이름인지 한 가족인지). 폰트 파일의 name table에서 실제 이름을 읽어 테마에 반영(프로토타입에서 확인).
  - 폰트 파일은 `assets/fonts/`에 둠: `NanumSquareL.ttf`(Light), `NanumSquareR.ttf`(Regular), `NanumSquareB.ttf`(Bold), `NanumSquareEB.ttf`(ExtraBold). 비`ac` 계열로 통일하고 `ac` 세트와는 섞지 않음(`ac`의 정확한 의미는 미확인). 진짜 Bold가 생겼으므로 앞서 논의한 가짜 굵게(faux bold)는 쓰지 않음.
  - 주의: PPTX에서 굵은 글씨는 `bold` 플래그를 켜면 PowerPoint가 `NanumSquareR`을 합성 굵게 처리할 수 있음. 굵은 구간은 폰트 이름 자체를 `NanumSquareB`/`NanumSquareEB`로 지정하는 방식을 프로토타입에서 확인(열람 PC에 해당 굵기 폰트가 설치되어 있어야 함).
  - 열람 PC에 폰트가 설치되어 있어야 PPTX가 같게 보임(생성 라이브러리는 폰트 임베드 미지원). 납품 시 폰트 파일 동봉/설치 안내 필요. HTML은 `@font-face`로, PDF는 인쇄 시 임베드되므로 영향 없음.
  - 폰트 라이선스는 사용 전에 확인(배포/임베드 조건).
  - **슬라이드를 통째로 이미지로 넣는 방식은 불가**(그러면 PDF와 다를 바가 없음). 네이티브 도형/텍스트로 만든다. 이미지는 복잡한 CSS 장식 영역에만 한정.
  - PPTX에 "수정 금지" 표시는 넣지 않는다.
- **HTML, PPTX, PDF는 모두 출력물이다.** 원본(SSOT)은 TSX(슬라이드당 1파일)이며 수정은 원본에서만 한다.
