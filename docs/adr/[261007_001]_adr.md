# ADR [261007_001]: 강의자료 생성 파이프라인 설계

- 날짜: 2026-10-07
- 관련 노트: [`docs/notes/[261007_001]_note.md`](../notes/[261007_001]_note.md)
- 범위: 결정된 사항만 기록한다. 논의 과정과 미결 사항은 노트를 참고한다.

## ADR-1. 산출물과 원본(SSOT)

**상태**: 확정

**맥락**
AI와 대화하며 만든 강의자료를 세 가지 형태로 제공해야 한다.

**결정**
- 산출물: 최종 강의자료는 **HTML**, 납품자료는 **PPTX**, 수강생 배포용은 **PDF**. 비율은 16:9.
- **HTML, PPTX, PDF는 모두 출력물**이다. 원본(SSOT)은 TSX이며 수정은 원본에서만 하고 다시 생성한다.
- PPTX를 직접 편집하지 않으므로 PPTX에 "수정 금지" 표시는 넣지 않는다.

**결과**
- 출력물의 직접 수정은 지원하지 않는다.

## ADR-2. 원본 형식: 슬라이드당 TSX 1파일

**상태**: 확정 (파일 구성은 [`[261007_002]_adr.md`](./[261007_002]_adr.md) ADR-2로 대체됨)

**맥락**
Markdown은 표, 그림, 텍스트 배치와 인라인 뱃지 표현에 한계가 있다. 사람과 AI가 모두 편집해야 한다.

**결정**
- 원본은 **TSX 컴포넌트**(선언형으로 제한)로 작성한다.
- **하나의 슬라이드는 1개의 tsx 파일**로 만든다.
- 슬라이드 순서와 메타는 `deck.ts` 매니페스트의 배열이 정한다. 파일명 번호(`s01-...`)는 읽기 편의용이다.
- 문구는 해당 슬라이드 파일 **맨 위의 `text` 객체**로 분리한다.
- 파일 구성: `decks/<이름>/deck.ts`, `decks/<이름>/slides/sNN-*.tsx`, `decks/<이름>/assets/`, 공용 컴포넌트는 `src/components/`.

**결과**
- AI 수정 범위가 한 파일로 한정되고 diff와 검토 단위가 슬라이드와 일치한다.
- AI가 만든 TSX를 서버에서 그대로 실행하는 것은 보안 위험이 있어, 서비스화할 때는 허용 컴포넌트와 props만 쓰게 제한해야 한다.
- 슬라이드에 반복문이나 조건문 같은 로직을 넣지 않는다.

## ADR-3. 인라인 서식은 세그먼트 배열로 표현

**상태**: 확정 (작성 방식은 [`[261007_003]_adr.md`](./[261007_003]_adr.md) ADR-8로 `t` 템플릿으로 바뀜. 타입과 헬퍼, 렌더링 구조는 그대로 유지됨. `badge()`는 [261008_003] ADR-5로 없앰)

**맥락**
한 문장 안에 일반 텍스트와 뱃지, 굵은 글씨가 섞이는 경우를 표현해야 한다. 문자열 안 문법은 파서와 이스케이프 부담이 있다.

**결정**
- 인라인 서식은 문자열과 인라인 요소를 섞은 **배열**로 표현한다.
  ```ts
  left: ["값을 담는 이름표", ["타입은 ", badge("동적", "green"), "으로 결정"]]
  ```
- 타입은 `Inline = string | Badge | Bold | Code | Link`, `Sentence = string | Inline[]`로 두고, 헬퍼 `badge()`, `bold()` 등을 제공한다.
- 인라인 요소는 `badge`, `bold`, `code` 세 가지로 시작하고 필요할 때 하나씩 추가한다.

**결과**
- 파서가 필요 없고 타입으로 검사된다. 배열 항목이 PPTX 텍스트 run과 1:1로 대응한다.
- 공백은 문자열에 직접 포함해야 한다(빠지면 단어가 붙는다).

## ADR-4. 출력 파이프라인: HTML 기준, 위치 추출 후 PPTX 포팅

**상태**: 채택 (프로토타입으로 어긋남 정도를 검증하고, 심하면 재검토. 슬라이드 본문 텍스트를 줄마다 텍스트박스로 내보내는 부분은 [`[261007_004]_adr.md`](./[261007_004]_adr.md) ADR-11로 대체됨. 장식 도형의 바깥 그림자를 이미지로 만들지 않는 것은 [261008_003] ADR-6으로 좁힘)

**맥락**
HTML이 디자인 표현력이 가장 높다. 그러나 HTML과 PPTX는 레이아웃 모델이 달라(흐름 vs 절대 좌표) 마크업을 직접 변환할 수 없다.

**결정**
- 파이프라인: **TSX → HTML(1920×1080 고정 스테이지) → Playwright로 렌더링하고 DOM에서 위치와 계산된 스타일 추출 → 장면 JSON → PPTX**. PDF는 HTML을 인쇄(`@page { size: 13.333in 7.5in }`)해서 만든다.
- 환산: 1920×1080px = 13.333×7.5in, 1px = 0.5pt, 좌표는 px × 6350 EMU.
- 추출 대상은 HTML에 `data-pptx="text|shape|image|table"`로 표시하고, 표시 없는 요소는 무시하거나 경고한다.
- PPTX는 **네이티브 요소**로 만든다.
  - 텍스트: `Range.getClientRects()`로 브라우저가 나눈 **줄 단위 텍스트와 좌표**를 읽어 줄마다 텍스트박스 하나, 자동 줄바꿈 끔, 내부 여백 0.
  - 뱃지: HTML 뱃지 좌표에 pill 도형을 배치하고 앞뒤 텍스트도 별도 텍스트박스로 고정.
  - 복잡한 CSS 장식(그라데이션, 복잡한 그림자 등) 영역만 PNG로 렌더링해 삽입한다.
  - **슬라이드를 통째로 이미지로 넣는 방식은 사용하지 않는다.**
  - 글자 세로 위치 차이는 폰트별 보정값으로 맞춘다.
- PPTX 생성 라이브러리는 `pptxgenjs`를 후보로 하고, 개발 스택은 Node/TypeScript로 한다.

**결과**
- PowerPoint가 줄바꿈을 다시 하지 않아 줄 수 차이 위험이 없다. 박스 폭 여유나 넘침 검사가 필요 없다.
- PPTX에서 직접 수정한 내용은 원본에 반영되지 않는다.

## ADR-5. 폰트: NanumSquare, 굵기는 역할이 결정

**상태**: 확정 (사용 굵기는 [`[261007_002]_adr.md`](./[261007_002]_adr.md) ADR-4로 R, B 두 가지로 축소됨)

**맥락**
HTML, PPTX, PDF에서 같은 글자 폭과 모양이 필요하다.

**결정**
- 폰트는 **NanumSquare**의 `L`(Light), `R`(Regular), `B`(Bold), `EB`(ExtraBold) 4종만 쓴다. 파일은 `assets/fonts/`에 둔다. `ac` 세트와는 섞지 않는다.
- 진짜 Bold가 있으므로 가짜 굵게(faux bold)는 쓰지 않는다.
- **굵기는 역할(테마 토큰)이 정하고, 텍스트 변수에는 문장 중간 강조만 `bold()`로 표시**한다. 텍스트 변수에 폰트 이름을 직접 쓰지 않는다.
  ```ts
  fonts: { heading: "NanumSquareEB", body: "NanumSquareR", emphasis: "NanumSquareB", caption: "NanumSquareL" }
  ```

**결과**
- PPTX를 열람하는 PC에 폰트가 설치되어 있어야 같게 보인다(생성 라이브러리는 폰트 임베드를 지원하지 않음). 납품 시 폰트 파일 동봉이나 설치 안내가 필요하다.
- HTML은 `@font-face`, PDF는 인쇄 시 폰트가 임베드되므로 영향이 없다.

## ADR-6. 커밋 메시지는 한글로 작성

**상태**: 확정

**결정**
- 커밋 메시지(제목과 본문)는 한글로 작성한다. 코드 식별자와 기술 용어는 원형을 유지한다.
- 이 규칙은 `CLAUDE.md`의 "규칙" 섹션에 반영되어 있다.
